A evolução do desenvolvimento de software, até o reuso [1]

Do primeiro programa armazenado em memória até o momento em que reaproveitar software deixou de ser exceção, na narrativa do capítulo [1].

1948 Manchester, SSEM Kilburn, Williams e Tootill: primeiro programa armazenado e executado na memória do computador.
1948 A base teórica Shannon [2] descreve a lógica binária, em substituição ao cartão perfurado.
Anos 1950 O software se separa do hardware Antes só fabricantes como a IBM produziam software; surgem as primeiras empresas independentes.
Anos 1950 A repetição vira mercado Processos de empresas se parecem, os programas saem parecidos: nasce a ideia de reaproveitar partes prontas.
Hoje A divisão que o reuso criou Reinventar a roda ou reusar. Frameworks e padrões de projeto são as principais ferramentas do reuso.
Takeaway

Com a orientação a objetos, o reuso deixou de ser desejável e passou a ser necessário para garantir um nível mínimo de qualidade no produto final.

Demonstração: o reuso dentro do próprio fork

Abrir o pom.xml do fork e contar em voz alta quantas linhas de dependência existem. Depois, rodar ./mvnw dependency:tree e ver quantos artefatos aquelas poucas linhas puxam.

# pom.xml, bloco <dependencies>: três linhas
spring-boot-starter-web
spring-boot-starter-data-jpa
spring-boot-starter-test

# ./mvnw dependency:tree, uma amostra do que essas três linhas puxam
+- spring-boot-starter-tomcat
+- spring-boot-starter-json
+- hibernate-core
+- jackson-databind
+- ... dezenas de outros artefatos
Pergunta para a turma

Quantas linhas de código o aluno escreveu para ter tudo isso? Nenhuma. É o reuso do capítulo, setenta anos depois, com outro nome e outra escala.

Exercício individual: pronto ou específico da Rota Sul

Cinco minutos, individual, no caderno. O objetivo é separar o que já existe pronto do que só a Rota Sul precisa.

O que escrever nos cinco minutos

  1. Três funcionalidades que a Rota Sul vai precisar e que certamente já existem prontas em algum lugar.
  2. Três funcionalidades que ninguém no mundo tem pronta, porque são específicas da Rota Sul.
  3. Duas ou três respostas em voz alta antes de seguir para o Ciclo 2.

Respostas típicas: do primeiro grupo, autenticação, geração de PDF, envio de e-mail, acesso a banco. Do segundo, a regra que decide se um pedido vira uma ou duas remessas, e o critério de escolha do parceiro na última milha.

Framework: o que orienta a estrutura do software [1]

Ferramenta que orienta o desenvolvedor a usar certos procedimentos para criar um software, apoiada em abstração, polimorfismo e herança. Um dos primeiros amplamente difundidos foi o SmallTalk MVC, que volta na Aula 06.

Reuso de partes prontas

Facilita implementar novos sistemas a partir de subsistemas inteiros já testados.

Classes mais específicas

Quanto mais específica cada classe, mais flexível o framework fica para segmentar o processamento.

Sistema expansível

Classes específicas facilitam acrescentar partes novas por meio de interfaces.

Ponto controverso

O framework passa a controlar a execução das classes e do software, tirando do desenvolvedor parte da responsabilidade de criar classes de controle. É o embrião da inversão de controle, formalizada na Aula 12.

02 Framework

Padrão de projeto: o que resolve um problema específico [1]

O framework orienta como estruturar o software que será desenvolvido; o padrão de projeto orienta como implementar a solução de um problema específico desse software. É a única diferença entre os dois.

Framework, na Rota Sul

A estrutura em camadas do sistema que organiza o atendimento, o pedido e o rastreamento é assunto de framework.

Padrão de projeto, na Rota Sul

Paginar em memória a consulta de ocorrências que o atendente faz ao telefone, sem ir ao banco a cada clique, é assunto de padrão de projeto.

No projetor

Site do Spring Boot ao lado do catálogo de um único padrão: um decide a forma do projeto inteiro, o outro resolve um ponto. Mesma aplicação, duas perguntas diferentes.

02 Padrão de projeto

Exercício em duplas: framework ou padrão de projeto

Cinco minutos, em duplas. Classificar quatro necessidades da Rota Sul em "framework" ou "padrão de projeto".

Classificar estas quatro necessidades

  1. Organizar o sistema em camadas de apresentação, negócio e dados.
  2. Evitar que dois expedidores criem duas remessas para o mesmo pedido.
  3. Mapear as tabelas do banco para objetos Java.
  4. Trocar o cálculo de frete conforme o parceiro, sem espalhar if pelo código.

Modelo de resposta: justificar, não só classificar. Exemplo: mapear tabelas para objetos é framework, porque decide a estrutura de código do sistema inteiro, e não resolve um problema pontual.

02 Exercício, framework ou padrão
10

Quiz de fixação

Segundo o capítulo, qual é a diferença entre framework e padrão de projeto?
  • A O framework orienta como implementar a solução de um problema específico do software, e o padrão de projeto orienta como estruturar o software como um todo.
  • B O framework orienta como o software a ser desenvolvido deve ser estruturado, e o padrão de projeto orienta como implementar a solução de um problema específico desse software.
  • C Framework e padrão de projeto são o mesmo conceito, e a escolha do termo depende da linguagem de programação usada.
  • D O framework serve para sistemas web e o padrão de projeto serve para sistemas desktop.

Laboratório, passo 2 de 2: as cinco linhas de framework

O que preencher

  1. Cinco linhas, todas dentro do contrato técnico da disciplina, projetado no quadro para consulta.
  2. Um problema por linha: estruturar a aplicação; expor operações por HTTP; gravar e ler dados relacionais sem SQL na mão; gerar as telas do portal no servidor; escrever testes automatizados.
  3. A Justificativa responde em uma frase por que esse framework, e não escrever na mão.

Conferência cruzada: troque de lugar com o colega ao lado e procure uma coisa só: justificativa que apenas repete a escolha, do tipo "escolhi Spring Boot porque Spring Boot é bom". Justificativa assim volta para o autor reescrever.

02 Laboratório, passo 2, framework
13

Laboratório, passo 3: as linhas de padrão de projeto

Aqui não se exige o nome canônico do padrão, catalogado só na Aula 11. Exige-se a descrição do problema específico e a forma da solução.

O que preencher

  1. Escolher pelo menos três destes problemas: evitar remessa duplicada; paginar em memória a consulta de ocorrências; variar o cálculo de frete sem espalhar condicionais; padronizar a criação de uma Remessa a partir de um Pedido.
  2. Na Escolha, descrever a solução em uma frase; se souber o nome do padrão, escrever entre parênteses.
Nota de rastreabilidade

Ao final do arquivo, um parágrafo dizendo quais linhas ainda são hipóteses e serão revisitadas mais adiante. Decisão registrada com data de revisão é decisão; decisão sem revisão é palpite.

Prévia da Aula 03

Hoje a Rota Sul foi tratada como um sistema só. Na próxima aula ela é tratada como o que de fato é: várias pessoas em lugares diferentes, trabalhando sobre a mesma entrega.

As duas ideias de hoje

Reuso é necessário para garantir qualidade mínima; e a diferença entre framework e padrão é uma só: framework estrutura o software, padrão resolve um problema específico dele.
