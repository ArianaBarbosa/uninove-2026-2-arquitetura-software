Os dois caminhos do desenvolvimento de software [1]

O capítulo abre descrevendo dois modos de trabalho, e uma frase que resume a diferença entre eles.

"Fazer e depois pensar no que foi feito"

Por questão cultural, o desenvolvedor constrói o software sem avaliar devidamente os problemas que ele pode ter, nem quando uma solução pode ser reaproveitada, e acaba replicando o que já foi desenvolvido. Se a parte replicada precisar mudar depois, o custo de atualização e reteste é alto.

"Pensar em como deve ser feito, e depois fazer"

O desenvolvedor segue regras de modelos de arquitetura, orientações de frameworks e padrões de projeto. É mais complexo, gasta mais tempo em planejamento, mas gasta bem menos tempo nas demais atividades.

A estimativa do capítulo

No Brasil, cerca de 10% do tempo de projeto vai para análise, 20% para programação, e o resto para correção de erros e alterações. Num país de cultura mais estruturada, como a Alemanha do exemplo do capítulo, a proporção se inverte: cerca de 60% para análise, 30% para programação e 10% para correção.

Origem histórica dos padrões de projeto, e o MVC [1]

Os padrões de projeto vêm de boas práticas definidas por desenvolvedores no início dos anos 1970, trocadas em congressos e seminários.

Dois problemas comuns, achados na troca de experiências

O primeiro: a relação entre interface de usuário, regras de negócio e base de dados, e como modificar uma dessas partes sem quebrar as outras duas. O segundo: a possibilidade de construir um novo software sem recomeçar do zero. O capítulo cita dois livros clássicos, GAMMA e JOHNSON [2] e LARMAN [3].

O MVC, primeiro exemplo do capítulo, cerca de 1975

Orienta a separação do código-fonte em três partes independentes: interação com o usuário (view), regras de negócio e acesso à base de dados (model), e algo que conecta as duas (controller). A analogia do capítulo: cada parte é uma peça de quebra-cabeça, com um desenho que encaixa nas outras.

Por que o MVC nasceu

Reduzir o tempo de desenvolvimento e teste em atualizações futuras: uma vez pronta, cada parte pode ser reaproveitada em novos softwares. Talvez seja o padrão de projeto mais usado entre os desenvolvedores.

O catálogo de padrões de projeto, GoF [2]

Os 23 padrões do livro Design Patterns: Elements of Reusable Object-Oriented Software se organizam em três famílias, pela pergunta que cada uma responde.

Nota para o professor. O capítulo apresenta a origem dos padrões e um único exemplo detalhado, o MVC; não organiza os 23 padrões em catálogo, e não nomeia Strategy nem Factory Method. Essa organização vem da própria bibliografia que o capítulo cita como referência, GAMMA, HELM, JOHNSON e VLISSIDES (1994), o livro "Gang of Four", GoF.

O que abre a porta, e de onde vem o resto

O capítulo abre a porta com a origem e o MVC; o catálogo, no próximo slide, vem de onde o próprio capítulo manda buscar.

As três famílias do catálogo GoF [2]

Os 23 padrões se organizam pela pergunta que cada família responde.

FamíliaPergunta que respondeExemplos do catálogo
CriacionaisComo um objeto é instanciadoFactory Method, Abstract Factory, Builder, Prototype, Singleton

Onde os dois padrões de hoje entram

Template Method, comportamental, a turma já usou na Aula 07 sem saber o nome. Os dois padrões de hoje são um de cada uma das outras duas famílias.

11 As três famílias
10

Strategy, comportamental

Define uma família de algoritmos, encapsula cada um numa classe própria e os torna intercambiáveis: o algoritmo pode variar independentemente de quem o usa.

Na Rota Sul: o cálculo do frete de um pedido muda de fórmula conforme quem faz a entrega, a frota própria na rota principal ou uma transportadora parceira na última milha. A operação é sempre a mesma, calcular o frete, mas o algoritmo muda, e a escolha acontece a cada pedido novo, em tempo de execução.

Diferente do que a Aula 07 fez

Em PedidoService, a implementação inteira é fixada uma vez, quando a aplicação sobe, pelo parâmetro de perfil. No Strategy de hoje, a escolha acontece de novo a cada chamada, dentro do processo em execução, com base num dado do próprio pedido.

11 Strategy
11

Factory Method, criacional

Define uma interface para criar um objeto, mas deixa que subclasses decidam qual classe concreta instanciar.

Na Rota Sul: quando o atendente registra uma ocorrência por telefone, ele informa o tipo, atraso ou extravio, e o sistema precisa instanciar a subclasse de Ocorrencia correspondente sem que o código que atende a ligação conheça as subclasses.

A diferença entre os dois, em uma frase

Strategy troca o algoritmo de uma operação que já tem um objeto para atuar; Factory Method troca qual objeto é criado, antes de qualquer operação acontecer sobre ele.

Quiz de fixação

Segundo o capítulo, qual das alternativas a seguir NÃO é característica de um design pattern?
  • A Apresenta um modelo de organização de classes para resolver um problema já conhecido.
  • B É resultado de uma boa prática de programação, aplicada para resolver problemas conhecidos.
  • C Provê um mecanismo para estruturar o software de modo organizado, facilitando manutenções futuras.
  • D Não pode ser aplicado em arquiteturas organizadas em camadas.

Laboratório, passo 2: o contrato da estratégia

Em pedido/domain, a interface CalculadoraDeFrete, com um único método. Sem anotação de framework: é domínio.

Laboratório, passo 3: a primeira estratégia

public class FreteRotaPropria implements CalculadoraDeFrete {

Laboratório, passo 4: a segunda estratégia

FreteTransportadoraParceira implements CalculadoraDeFrete, também em pedido/domain: adicional de 30% sobre a mesma tarifa base.

public class FreteTransportadoraParceira implements CalculadoraDeFrete {
  private static final BigDecimal TARIFA_BASE = new BigDecimal("15.00");
  private static final BigDecimal ADICIONAL = new BigDecimal("1.30");

  @Override
  public BigDecimal calcular(Pedido pedido) {
    return TARIFA_BASE.multiply(ADICIONAL).setScale(2, RoundingMode.HALF_UP);
  }
}

15.00 multiplicado por 1.30 resulta em 19.50, representando o repasse pago ao parceiro da última milha.

Laboratório, passo 5: o contexto do Strategy (1/2)

Em pedido/service, CalculoDeFreteService, anotada @Service, recebendo as duas estratégias pelo construtor.

@Service
public class CalculoDeFreteService {
  private final CalculadoraDeFrete rotaPropria;
  private final CalculadoraDeFrete transportadoraParceira;

  public CalculoDeFreteService(FreteRotaPropria rotaPropria,
      FreteTransportadoraParceira transportadoraParceira) {
    this.rotaPropria = rotaPropria;
    this.transportadoraParceira = transportadoraParceira;
  }
}

O construtor guarda as duas estratégias concretas. É o único ponto do código que vai conhecer as duas ao mesmo tempo.

Laboratório, passo 5: o contexto do Strategy (2/2)

O método calcular decide qual estratégia chamar olhando pedido.getRegiao().

public BigDecimal calcular(Pedido pedido) {
  if ("ULTIMA_MILHA".equals(pedido.getRegiao())) {
    return transportadoraParceira.calcular(pedido);
  }
  return rotaPropria.calcular(pedido);
}

Laboratório, passo 8: a hierarquia de criadores

Também em rastreamento/domain, a classe abstrata OcorrenciaCreator. registrar é final; criarOcorrencia é o Factory Method, abstrato.

public abstract class OcorrenciaCreator {
  public final Ocorrencia registrar(String codigoRastreio) {
    if (codigoRastreio == null || codigoRastreio.isBlank()) {
      throw new IllegalArgumentException("codigo de rastreio e obrigatorio");
    }
    return criarOcorrencia(codigoRastreio, LocalDateTime.now());
  }

  protected abstract Ocorrencia criarOcorrencia(
      String codigoRastreio, LocalDateTime registradaEm);
}

Duas subclasses: AtrasoOcorrenciaCreator devolve new OcorrenciaAtraso(...) e ExtravioOcorrenciaCreator devolve new OcorrenciaExtravio(...).
