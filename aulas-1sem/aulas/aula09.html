Metadados: o que são, e por que existem [1]

Um metadado, ou metainformação, é informação a respeito de outros dados, e existe desde os anos 1970.

A trajetória, segundo o capítulo

Nos anos 1970, usado para armazenar dados dos próprios aplicativos. Depois, para comunicação entre aplicativos e compartilhamento de informação. Nos anos 1990, a Internet trouxe XML e JSON, baseados em padrões abertos.

Por que texto simples

É o formato mais fácil de processar e transmitir pela rede. XML e JSON podem ser escritos e lidos por rotinas de qualquer linguagem de programação, e deixam os nomes dos metadados livres para o desenvolvedor escolher.

O gancho com a Aula 07

O capítulo já afirma que arquivos JSON ou XML "podem ser usados como protocolos ou interfaces de comunicação": é a mesma ideia de contrato de serviço da SOA, aplicada ao formato dos dados.

XML, eXtensible Markup Language [1]

Recomendação do consórcio W3C: linguagem de marcação projetada segundo cinco princípios.

Os cinco princípios do capítulo

  • Separar o conteúdo da formatação, em arquivos DTD
  • Ser entendível por máquinas e por seres humanos
  • Não ter limite na quantidade de tags criadas
  • Servir de agente de transporte entre sistemas distintos
  • Manter o foco no conteúdo, não na aparência

Estrutura

Uma tag inicial declara a versão do XML e a codificação de caractere. As demais tags são hierárquicas, sempre em pares de abertura e fechamento, e podem representar coleções de dados repetidas.

09 XML, princípios e estrutura
6

A desvantagem que o capítulo aponta [1]

A quantidade de bytes gasta com o nome das tags, comparada ao conteúdo que elas carregam.

<nome>Bilbo Bolseiro</nome>

A contagem do capítulo: treze bytes para as tags de abertura e fechamento, contra catorze bytes de conteúdo. Dos vinte e sete bytes do trecho, quase metade é informação que o aplicativo descarta rapidamente, o que pesa quando a tarifação é por volume de bytes transmitido.

Segunda desvantagem

Abrir e fechar cada tag também deixa mais lento tanto gerar quanto ler arquivos XML.

Demonstração: contando bytes num XML da Rota Sul

Repetir, com a turma, a mesma contagem do capítulo, agora com um Volume da Rota Sul.

<volume><etiqueta>VOL-001</etiqueta><pesoKg>12.5</pesoKg></volume>

No quadro

  1. Escrever o XML acima.
  2. Contar, com a turma, quantos bytes são de tag e quantos são de conteúdo.

O resultado da contagem: 55 dos 66 bytes do trecho são tag, 11 são conteúdo, quase 83% em tags, bem acima dos 48% do exemplo do capítulo. A causa: etiqueta e pesoKg são nomes mais longos do que os valores curtos que carregam, o que piora ainda mais a mesma desvantagem.

JSON, JavaScript Object Notation [1]

Alternativa popular ao XML, criada como padrão de baixo custo de processamento para o cliente e o servidor web trocarem informação.

Três características do capítulo

  • Coleção de dados nome : valor, tratada como vetor
  • Estrutura entendida por seres humanos e por máquinas
  • Subconjunto do JavaScript, mas independente da linguagem

Estrutura

{ e } delimitam o escopo dos dados, [ e ] delimitam coleções repetidas, sempre com o par "nome": "valor" separado por vírgula.

A vantagem sobre o XML

As mesmas vantagens do XML, mas com uso menor de bytes, por não depender de tags, e mais simples de escrever um interpretador para ele.

09 JSON

Negociação de conteúdo: como um endpoint fala dois formatos

O capítulo apresenta XML e JSON como dois formatos, mas não trata de como um mesmo endpoint escolhe entre eles: isto é técnica de HTTP e do framework web, posterior ao material, e é a aplicação prática do que o próprio capítulo já estabelece.

O cabeçalho Accept

O cliente que chama a API da Rota Sul diz em que formato quer a resposta, application/json ou application/xml.

Os dois conversores do Spring

O conversor para JSON, via Jackson, já vem com o spring-boot-starter-web. Acrescentando jackson-dataformat-xml ao classpath, um segundo conversor fica disponível, e o Spring escolhe entre os dois comparando o Accept com o que o endpoint declara que produz.

Quiz de fixação

Segundo o capítulo, qual das afirmações a seguir NÃO é um princípio correto sobre o uso de JSON?
  • A É facilmente entendido tanto por seres humanos quanto por máquinas.
  • B Usa um número maior de bytes do que o XML para representar os mesmos metadados.
  • C Pode ser gerado e interpretado em qualquer linguagem de programação.
  • DO escopo das coleções de dados é delimitado por caracteres simples, { e }, e [ e ].

Laboratório, passo 2: escrever o domínio

Em expedicao/domain, a classe Remessa, com id, codigoRastreio, previsaoEntrega e situacao.

@JacksonXmlRootElement(localName = "remessa")
public class Remessa {
  private Long id;
  private final String codigoRastreio;
  private final LocalDate previsaoEntrega;
  private String situacao;
  // construtor, getters e o setter de situacao no kit
}

A única exceção à regra da Aula 06. Sem @JacksonXmlRootElement, a tag raiz do XML sairia com o nome da classe Java, Remessa, em vez do nome de domínio em português. É anotação de serialização, não de persistência nem de web: a exceção fica registrada aqui e não vira regra geral.

Laboratório, passo 4: escrever o serviço

RemessaService, anotada @Service, delegando ao repositório.

@Service
public class RemessaService {
  private final RemessaRepository remessaRepository;
  public RemessaService(RemessaRepository remessaRepository) {
    this.remessaRepository = remessaRepository;
  }
  public Remessa buscarPorId(Long id) {
    return remessaRepository.buscarPorId(id);
  }
}

Laboratório, passo 5: adicionar o módulo Jackson XML

No pom.xml, a dependência que dá ao Spring o segundo conversor de mensagem HTTP.

<dependency>
  <groupId>com.fasterxml.jackson.dataformat</groupId>
  <artifactId>jackson-dataformat-xml</artifactId>
</dependency>

Sem ela, o Spring só tem o conversor de JSON disponível, e qualquer pedido de XML recebe 406 Not Acceptable.

Laboratório, passo 6: escrever o controlador

RemessaController, mapeado em /remessas, declarando os dois formatos que produz.

@RestController
@RequestMapping("/remessas")
public class RemessaController {
  private final RemessaService remessaService;
  public RemessaController(RemessaService remessaService) {
    this.remessaService = remessaService;
  }

  @GetMapping(value = "/{id}",
      produces = { MediaType.APPLICATION_JSON_VALUE, MediaType.APPLICATION_XML_VALUE })
  public Remessa buscarPorId(@PathVariable Long id) {
    return remessaService.buscarPorId(id);
  }
}

Laboratório, passo 9: registrar a decisão

Em docs/decisoes.md, uma linha explicando a escolha de um único endpoint com negociação de conteúdo.

O que a linha precisa dizer

Um único endpoint respondendo nos dois formatos, em vez de dois endpoints separados, porque um único recurso deve ter uma única URI, princípio que a Aula 10, sobre REST, vai formalizar.
