A origem histórica da comunicação remota [1]

O primeiro sistema com necessidade de comunicação remota, e a solução genérica que a Internet passou a exigir duas décadas depois.

SABRE, anos 1950

Desenvolvido pela IBM para a American Airlines gerenciar reservas. Um servidor central numa pequena cidade de Nova Iorque, acessado por terminais espalhados pelos Estados Unidos, processando cerca de 83 mil chamadas por dia. Abriu caminho para soluções proprietárias (IBM, Unisys, NCR, Honeywell), até a ARPANET virar Internet e exigir padrões abertos.

RPC, Remote Procedure Call, 1976

Implementação de software para compartilhamento remoto de recursos: um programa chama e executa outro, em outro computador da rede, como se a chamada fosse local. Popularizou-se com pacotes dos fabricantes Unix. As plataformas de desenvolvimento incorporaram: RMI para Java, DCOM para .Net.

Gancho

RMI é a implementação de RPC para a plataforma Java, o assunto do próximo slide.

RMI, Remote Method Invocation [1]

O cliente invoca um aplicativo no servidor, envia uma mensagem com os dados e espera a resposta. O servidor precisa estar sempre em execução.

Cinco cuidados que o capítulo exige

  • Tratar falha de rede, no cliente e no servidor
  • Considerar falha no aplicativo do servidor
  • Trocar informação só por mensagens, nunca por referência de memória
  • Aceitar queda de desempenho
  • Servidor saber sempre quem pediu, de modo seguro

Vantagem e desvantagem

O objeto remoto se usa como instância local, e a segurança é reforçada porque o acesso só acontece pela interface. Mas o software inteiro precisa ser Java, e mudanças na política de segurança da JVM podem exigir atualizar classes já escritas.

RMI entra hoje como leitura, não como laboratório: o exercício prático da aula é sobre SOAP e REST, que é o que a Rota Sul de fato vai construir daqui a pouco.

Demonstração: o preço da transparência de localização

public interface ServicoPotencia extends Remote {
  BigInteger quadrado(int numero) throws RemoteException;
  BigInteger potencia(int numero, int potencia) throws RemoteException;
}
A diferença de assinatura

Toda chamada remota pode falhar por rede, e a linguagem obriga o desenvolvedor a admitir isso já na assinatura do método; PedidoService, uma chamada local, não precisa admitir isso, porque não atravessa rede nenhuma.

SOAP, Simple Object Access Protocol [1,2]

Especificação para troca de dados estruturados entre aplicativos, começada na Microsoft e hoje coordenada pela W3C. Exemplo do capítulo: a consulta de CEP dos Correios.

Estrutura fixa da mensagem

Envelope identifica o XML como mensagem SOAP; Header, opcional, leva informação da aplicação, como autenticação; Body traz o conteúdo real; Fault, dentro do Body, carrega erro e status.

mustUnderstand e JAX-WS

O atributo diz se um elemento do cabeçalho é obrigatório (1) ou opcional (0) para quem recebe. Em Java, a API JAX-WS, com @WebService, @WebMethod e @WebParam, substitui a escrita manual do XML.

10 SOAP

REST, Representational State Transfer [1]

Ao contrário do SOAP, que troca arquivos XML, o REST foca o protocolo HTTP e as URIs: recursos identificados por URI, manipulados pela interface padrão do próprio HTTP.

JAX-RS, na plataforma Java EE

Anotações como @Path, @GET e @Produces(MediaType.APPLICATION_JSON) declaram o que cada recurso responde. A resposta chega direto na barra de endereço do navegador, sem envelope.

Nota para o professor

O capítulo não fala de springdoc-openapi: a ferramenta é posterior ao material. Mas resolve o mesmo problema que o capítulo chama, na Aula 07, de Descrição de Serviço, gerando a descrição de /remessas a partir do código, o mesmo papel que o WSDL cumpre para o SOAP.

Contraste dos três modelos, para fechar o ciclo

RMI só funciona entre aplicativos Java; SOAP e REST são neutros quanto a linguagem e sistema operacional.

ModeloFormato de dadoProtocolo de transporteSó funciona em Java?
RMIObjetos Java nativos, sem XMLProtocolo próprio do RMI sobre TCPSim
SOAPXML, com envelope inteiroHTTP ou SMTPNão
RESTO que o servidor decidir produzirHTTPNão
A diferença entre SOAP e REST

SOAP exige o envelope XML inteiro, com header, body e fault; REST é mais leve, apoiado só em HTTP, URIs e na representação do recurso, que a Aula 09 já mostrou poder ser JSON ou XML.

Quiz de fixação

A Rota Sul vai se conectar a um parceiro legado que só entende XML. Qual dos três modelos do capítulo NÃO permite transferir dados em XML?
  • A RMI, porque troca objetos Java diretamente, sem arquivos XML.
  • BSOAP, porque suas mensagens usam sempre arquivos em formato JSON, e não XML.
  • C REST, porque seus recursos nunca podem ser representados em XML.
  • D Nenhum dos três, porque todos usam XML obrigatoriamente.

Laboratório: o parceiro legado, simulado dentro do fork

A Rota Sul não tem um parceiro real para a turma acessar, então o laboratório simula o parceiro dentro do próprio fork: um endpoint SOAP simples, em br.uni9.rotasul.parceiro.

O que chega pronto no kit

parceiro.xsd, o contrato do serviço, e WebServiceConfig.java, que publica o servlet em /ws/* e expõe o WSDL a partir do XSD. Escrever isso à mão consumiria o laboratório inteiro sem ensinar nada sobre objetos remotos.

O que o aluno escreve hoje

Três peças: o @Endpoint que atende, o cliente que chama, e o teste que prova. É o mesmo tipo de código que se escreveria para consumir um parceiro de verdade; só o endereço muda.

Laboratório, passo 2: dependências e o gerador de classes

No pom.xml: spring-boot-starter-web-services, wsdl4j, e o jaxb2-maven-plugin apontando para o parceiro.xsd.

<plugin>
  <groupId>org.codehaus.mojo</groupId>
  <artifactId>jaxb2-maven-plugin</artifactId>
  <version>3.2.0</version>
  <configuration>
    <sources><source>src/main/resources/parceiro.xsd</source></sources>

A versão precisa ser dita em voz alta. A 2.x gera classes com javax.xml.bind; o Spring Boot 3 usa jakarta.xml.bind, e o marshaller do passo 6 não reconhece a linha antiga. Sem <version>, o Maven pode resolver a 2.x.

Laboratório, passo 4: escrever o endpoint que simula o parceiro

Em parceiro/endpoint, ParceiroEndpoint, anotado @Endpoint.

@Endpoint
public class ParceiroEndpoint {
  static final String NAMESPACE = "http://rotasul.uni9.br/parceiro";

  @PayloadRoot(namespace = NAMESPACE, localPart = "consultaEntregaRequest")
  @ResponsePayload
  public ConsultaEntregaResponse consultarEntrega(
      @RequestPayload ConsultaEntregaRequest request) {
    ConsultaEntregaResponse response = new ConsultaEntregaResponse();
    boolean daRotaSul = request.getCodigoRastreio().startsWith("RS");
    response.setSituacao(daRotaSul ? "EM_TRANSITO" : "DESCONHECIDO");
    // previsaoEntrega no kit completo
    return response;
  }
}

Laboratório, passo 6: escrever o cliente

Em parceiro/client, ParceiroClient, estendendo WebServiceGatewaySupport.

public class ParceiroClient extends WebServiceGatewaySupport {
  public ConsultaEntregaResponse consultarEntrega(String codigoRastreio) {
    ConsultaEntregaRequest request = new ConsultaEntregaRequest();
    request.setCodigoRastreio(codigoRastreio);
    return (ConsultaEntregaResponse)
        getWebServiceTemplate().marshalSendAndReceive(request);
  }

  public void apontarPara(String uri) {
    getWebServiceTemplate().setDefaultUri(uri);
  }
}

A URI não fica escrita dentro da classe. Um bean Jaxb2Marshaller, no kit, lê a propriedade rotasul.parceiro.uri, que vale http://localhost:${server.port:8080}/ws.

Laboratório, passo 7: testar o cliente

ParceiroClientTest, com a porta de @LocalServerPort e o cliente apontado para ela antes da chamada.

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class ParceiroClientTest {
  @LocalServerPort int porta;
  @Autowired ParceiroClient parceiroClient;

  @Test
  void devolveEmTransitoParaCodigoDaRotaSul() {
    parceiroClient.apontarPara("http://localhost:" + porta + "/ws");
    var resposta = parceiroClient.consultarEntrega("RS12345");
    assertEquals("EM_TRANSITO", resposta.getSituacao());
  }
}

O webEnvironment não é detalhe. No modo padrão (MOCK), a chamada SOAP não tem para onde ir. RANDOM_PORT sobe o Tomcat numa porta livre.
