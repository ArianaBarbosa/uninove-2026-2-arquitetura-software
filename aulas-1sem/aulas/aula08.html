Servidor, em geral, e as aplicações de grande porte [1]

O capítulo usa redes sociais como Facebook, WhatsApp, Instagram e Youtube para chegar à definição de servidor de aplicações.

Servidor, em geral

Provê algum tipo de serviço aos usuários: armazenamento de dados, correio eletrônico, compartilhamento de arquivos, e os servidores web, usados para hospedar e executar aplicativos na Internet.

Quatro requisitos comuns

  • Uso intensivo de uma rede de dados
  • Autenticação de usuários e gerenciamento do conteúdo
  • Sistema eficiente de armazenamento de dados
  • Sincronização entre o que é exibido no browser e no dispositivo móvel

De aplicação a plataforma, e a definição de servidor de aplicações [1]

Quando uma aplicação fica complexa o bastante para que outros aplicativos usem seus recursos, ela deixa de ser entendida só como aplicação.

Dois requisitos extras

Verificar se o aplicativo que quer usar os recursos é uma fonte segura, e verificar quais informações do usuário ele pode acessar. Consequência: a comunicação entre aplicativos remotos, e entre os servidores que os executam, precisa ser segura.

A definição do capítulo

Servidor de aplicações é "uma ferramenta para desenvolver e executar aplicações de grande porte". Além do Facebook, o capítulo enquadra aqui os sistemas colaborativos, os sistemas corporativos como automação bancária, e os ERP.

O gancho para o Ciclo 1 continuar

Java EE é uma das plataformas que resolve essa necessidade, com frameworks, modelos de programação e APIs prontas para os serviços de infraestrutura.

Java EE: os problemas que resolve, e quem usa no mercado [1]

Para ser usada, a Java EE precisa de um servidor de aplicações: é a forma pela qual a plataforma chega ao desenvolvedor.

Problemas de infraestrutura que resolve

  • Segurança no acesso às informações
  • Garantia de disponibilidade dos serviços
  • Balanceamento da carga de uso dos servidores
  • Gerenciamento das bases de dados usadas pela aplicação

Servidores usados no mercado

JBoss e WebSphere, sobre Linux ou Windows. No .Net, o servidor de aplicações é qualquer versão do Windows Server, não uma ferramenta específica.

As quatro regras do capítulo: seguir os padrões da Java EE, prover serviços de infraestrutura, gerenciar comunicação entre servidores e, quando possível, disponibilizar frameworks.

As tecnologias da plataforma Java EE [1]

O capítulo lista dez tecnologias, cada uma com especificação e uso próprios, para os requisitos mais comuns de aplicações de grande porte.

  • EJB, componentes reutilizáveis dentro e fora do servidor
  • JAX-WS, web services baseados em Servlets e EJBs
  • RMI, comunicação remota entre componentes Java, assunto da Aula 10
  • JNDI, acesso a serviços de nomenclatura e diretório na rede
  • JDBC, acesso a bancos de dados relacionais
  • JTA e JTS, transações remotas e o acompanhamento delas
  • JMS, componentes que executam transações por troca de mensagens
  • Java Web, JSP e Servlets, base de muitos frameworks
  • JSF, componentes reutilizáveis do lado do servidor, assunto da Aula 18
  • JPA, persistência sem escrever todo o SQL à mão, assunto das Aulas 15 e 16

As vantagens do Java EE, e a conclusão do capítulo [1]

Seguindo os padrões e sem usar função específica de um fornecedor, o aplicativo roda em qualquer servidor de aplicações, independentemente de quem o fabricou.

As vantagens, segundo o capítulo

  • Agilidade no desenvolvimento
  • Qualidade mais efetiva, por componentes já testados e reusados
  • Flexibilidade para vários modelos de arquitetura
  • Reuso de componentes em outros aplicativos

A conclusão do capítulo

"Um servidor de aplicações é o ambiente que permite desenvolver e executar aplicações de grande porte baseadas em modelos de arquitetura distribuída, usado porque já traz pronta a implementação dos serviços da plataforma."

O contraste com o laboratório da Rota Sul

O capítulo descreve o aplicativo Java EE como algo "instalado no servidor de aplicações que será usado", sem usar o termo WAR: é complemento de leitura atual, explicado abaixo.

WAR, o formato padrão da Java EE clássica. Sigla de Web Application Archive, um arquivo que contém só o código da aplicação e pressupõe um servidor de aplicações já instalado e em execução para interpretá-lo. É esse modelo, WAR mais servidor administrado à parte, que o laboratório de hoje contrasta com o .jar executável usado desde a Aula 01.

No modelo do capítulo

O desenvolvedor empacota a aplicação num WAR, só o código dela, e instala num servidor de aplicações, JBoss ou WebSphere, administrado à parte, que fornece segurança, transação, diretório e pool de conexão via as APIs da Java EE.

No laboratório da disciplina

O Spring Boot embarca o próprio servidor web dentro do .jar: não há servidor de aplicações separado, e java -jar já sobe a aplicação inteira. Boa parte do que JTA, JNDI e EJB resolvem tem hoje equivalente dentro do próprio Spring, tema da Aula 12.

Demonstração: o que tem dentro do .jar executável

Abrir o pacote gerado pelo ./mvnw clean package e olhar o que está lá dentro.

No projetor

  1. Rodar ./mvnw clean package e, ao terminar, jar tf target/*.jar | head -30.
  2. Localizar BOOT-INF/classes, as classes do aluno, BOOT-INF/lib, o Tomcat embarcado e as demais dependências, e META-INF/MANIFEST.MF.
  3. Abrir o manifesto com unzip -p target/*.jar META-INF/MANIFEST.MF e apontar Start-Class, a classe do aluno, e Main-Class, o launcher do próprio Spring Boot.

É esse launcher que sobe o Tomcat embarcado antes de entregar o controle à aplicação do aluno.

Laboratório, passo 1: confirmar o empacotamento

Abrir o pom.xml do fork e localizar o plugin dentro de <build><plugins>.

<plugin>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-maven-plugin</artifactId>
</plugin>

É esse plugin que transforma o .jar comum, que só teria o código do aluno, num .jar executável, com o Tomcat e as demais dependências embutidos.

Laboratório, passo 3: rodar com java -jar

Num terminal novo, sem nenhum ./mvnw envolvido.

java -jar target/*.jar
# noutro terminal, trocando 8080 pela porta que o seu terminal imprimiu
curl http://localhost:8080/pedidos

Conferir a mesma inicialização e a mesma linha de porta de sempre. Nenhum servidor de aplicações foi instalado para isso acontecer.
