O que é um framework, na definição do capítulo [1]

Um framework é uma solução para um problema específico que ainda não é software executável por si só: um conjunto de bibliotecas associadas a interfaces que permitem acoplá-las ao software em desenvolvimento.

A frase central do capítulo. "Um framework determina como o aplicativo funcionará, pois ele é que controla o fluxo de execução de operações que o aplicativo necessita. A isso se dá o nome de inversão de controle."

A direção da chamada se inverte

Numa biblioteca comum, é o próprio programa que decide quando chamar cada função. Com um framework, é ele que decide quando chamar o código da Rota Sul, não o contrário. O exemplo do capítulo é gráfico: os componentes de interface do Android permitem implementar telas sem escrever cada botão do zero.

Framework contra padrão de projeto, e cinco vantagens [1]

O capítulo repete a distinção já usada nas Aulas 02 e 11: padrões de projeto orientam a implementação; um framework inclui a implementação de código.

Framework pode conter vários padrões

Mas sempre tem domínio de uma aplicação particular, o que os padrões de projeto, sozinhos, não têm. Strategy e Factory Method da Aula 11 não sabem nada sobre a Rota Sul; o Spring, como framework, é acoplado a como a Rota Sul roda.

Cinco vantagens do capítulo

Facilidade para detectar erros; garantia melhor de qualidade; o desenvolvedor se concentra no aplicativo final; reuso de soluções conhecidas; uso otimizado de recursos.

12 Framework contra padrão
6

A desvantagem central, e frameworks de empresa [1]

O código-fonte do framework normalmente não é editável, de propósito: a intenção é formar o núcleo do aplicativo e adicionar blocos de código novos em torno dele.

O capítulo soma a isso o aumento de tamanho final do software, classes de acoplamento desnecessárias num aplicativo do zero, e o tempo de aprendizado: se gasto durante a execução do projeto, pode anular o ganho de produtividade esperado.

Frameworks de empresa, exemplo do capítulo

Além de frameworks genéricos, como o próprio Spring, empresas com problemas específicos justificam um framework próprio: a Sony, para o processamento de imagens de suas câmeras, e a Ericsson, para as centrais de comunicação telefônica que produz.

Demonstração: quem chama o construtor de PedidoServicePadrao

Abrir PedidoServicePadrao e PedidoServiceComAnaliseDeRisco, da Aula 07: nenhuma das duas classes chama a outra, nenhuma decide qual vai rodar.

@Service
@Profile("padrao")
public class PedidoServicePadrao implements PedidoService { ... }

@Service
@Profile("risco")
public class PedidoServiceComAnaliseDeRisco implements PedidoService { ... }

Quem decide é o spring.profiles.active do application.properties, lido pelo Spring antes de qualquer linha do código da Rota Sul executar. O framework decide o quê instanciar e quando; o desenvolvedor só descreve as opções.

Anatomia do container: o que o Spring faz ao subir [4]

Quando ./mvnw spring-boot:run executa, o Spring varre o código em busca de candidatos a bean.

Nota para o professor. O capítulo apresenta a inversão de controle em nível conceitual; ele não descreve o mecanismo interno do container (varredura de candidatos, resolução de @Profile, injeção por construtor). Essa camada vem da documentação oficial do Spring Framework [4], necessária para o laboratório de hoje ser executável.

O mecanismo, não mágica

Classes @Component, @Service, @Repository, e métodos @Bean em classes @Configuration; se a definição tiver @Profile, só ativa quando o perfil está entre os ativos. Só depois de resolver todas as definições o container instancia e injeta, como em PedidoController recebendo PedidoService.

Configuração implícita contra configuração explícita

Duas formas de registrar um bean com perfil, e o laboratório de hoje pede a segunda.

Implícita, o que a Aula 07 já fez

Anotar a própria classe de implementação com @Service e @Profile("padrao"). Funciona bem quando a decisão é simples, mas a decisão de qual perfil usa qual classe fica espalhada, uma anotação por classe.

Explícita, o que o laboratório de hoje pede

Uma classe @Configuration concentra, num único lugar, a decisão de qual implementação vira bean em qual perfil, por métodos @Bean. As classes de implementação não precisam de anotação nenhuma.

A vantagem pedagógica

Quem lê a classe de configuração vê, de uma vez, o mapa inteiro de "qual implementação em qual ambiente", sem abrir cada classe candidata para procurar @Profile.

12 Implícita contra explícita

Demonstração: anatomia de uma classe @Configuration

Esqueleto de uma classe qualquer, para mostrar a anatomia antes de escrever a de hoje.

@Configuration
public class ExemploConfig {
  @Bean
  @Profile("dev")
  public MinhaInterface implementacaoDeDev() { return new ImplementacaoDeDev(); }

  @Bean
  @Profile("prod")
  public MinhaInterface implementacaoDeProd() { return new ImplementacaoDeProd(); }
}

O @Profile decide se o método participa da subida; o tipo de retorno é o que fica disponível para o construtor que pedir a interface, não o tipo concreto. Só um dos dois métodos roda por subida.

Quiz de fixação

Segundo o capítulo, quando um desenvolvedor usa um framework, quem controla o fluxo de execução das operações que o aplicativo necessita?
  • A O próprio desenvolvedor, chamando cada função do framework na ordem que escolher.
  • B O framework, que determina como o aplicativo vai funcionar: a inversão de controle.
  • C O sistema operacional, que agenda a execução de cada classe do framework por prioridade.
  • D Framework e aplicativo rodam em processos independentes, sem relação de controle entre os dois.

Laboratório, passo 1: o contrato de notificação

Em rastreamento/service, a interface NotificadorDeOcorrencia, com um único método. Sem anotação de framework: é contrato.

public interface NotificadorDeOcorrencia {
  void notificar(Ocorrencia ocorrencia);
}

Como toda interface de contrato do semestre, ela não sabe que o Spring existe. Ocorrencia, já entregue na Aula 11, é o tipo que ela recebe.

Laboratório, passo 2: a implementação de dev

NotificadorDeOcorrenciaConsole, também em rastreamento/service, sem anotação nenhuma.

public class NotificadorDeOcorrenciaConsole implements NotificadorDeOcorrencia {

  @Override
  public void notificar(Ocorrencia ocorrencia) {
    log.info("[DEV] ocorrencia {} do tipo {} registrada",
        ocorrencia.getCodigoRastreio(), ocorrencia.getTipo());
  }
}

Registra no log, via Logger do SLF4J, o código de rastreio e o tipo da ocorrência. Quem registra esta classe como bean é NotificacaoConfig, no passo 4, nunca uma anotação aqui.

Laboratório, passo 3: a implementação de prod

NotificadorDeOcorrenciaWebhookSimulado, recebendo urlWebhook pelo construtor, também sem anotação.

public class NotificadorDeOcorrenciaWebhookSimulado implements NotificadorDeOcorrencia {
  private final String urlWebhook;
  public NotificadorDeOcorrenciaWebhookSimulado(String urlWebhook) {
    this.urlWebhook = urlWebhook;
  }

  @Override
  public void notificar(Ocorrencia ocorrencia) {
    log.info("[PROD] enviaria POST para {} com a ocorrencia {}",
        urlWebhook, ocorrencia.getCodigoRastreio());
  }
}

Sem chamada de rede real, só log. Simulado de propósito, pela mesma razão da Aula 10: a aula não pode depender de um endpoint externo de verdade em qualquer sala.

Laboratório, passo 4: registrar os dois beans, explicitamente

Criar NotificacaoConfig, anotada @Configuration, em rastreamento/service.

@Configuration
public class NotificacaoConfig {

  @Bean
  @Profile("dev")
  public NotificadorDeOcorrencia notificadorDeOcorrenciaDev() {
    return new NotificadorDeOcorrenciaConsole();
  }

  @Bean
  @Profile("prod")
  public NotificadorDeOcorrencia notificadorDeOcorrenciaProd(
      @Value("${rotasul.webhook.parceiro-notificacao}") String urlWebhook) {
    return new NotificadorDeOcorrenciaWebhookSimulado(urlWebhook);
  }
}

Laboratório, passo 6: comprovar por log

Ainda em NotificacaoConfig, um terceiro @Bean, do tipo CommandLineRunner.

@Bean
@Profile({"dev", "prod"})
public CommandLineRunner logarNotificadorAtivo(NotificadorDeOcorrencia notificador) {
  return args -> log.info("Notificador ativo: {}",
      notificador.getClass().getSimpleName());
}

Este bean precisa de @Profile, e não pode ficar sem. O construtor pede NotificadorDeOcorrencia, que só existe sob dev ou prod. Sem a restrição, ele tentaria subir também sob padrao, o perfil ativo desde a Aula 07, onde não há notificador nenhum, e quebraria a suíte inteira.

Laboratório, passo 7: instalar o ajuste em PedidoServicePadrao

Copiar do kit: PedidoServicePadrao.java, com o @Profile ampliado de "padrao" para os três perfis.

@Service
@Profile({"padrao", "dev", "prod"})
public class PedidoServicePadrao implements PedidoService { ... }

Um segundo ponto de fiação que só o contexto Spring inteiro expõe. PedidoController pede PedidoService em toda subida, mas PedidoServicePadrao só era bean sob "padrao". O que muda hoje

Na Aula 11 a Rota Sul decidiu, dentro do próprio código, qual estratégia de frete usar. Hoje o container do Spring decidiu, fora do código de negócio, qual notificador injetar: as duas são formas legítimas de trocar comportamento, e a diferença é exatamente o que separa um padrão de projeto de uma característica de framework.
