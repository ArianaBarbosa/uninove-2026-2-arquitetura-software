Componente de software e comunicação entre componentes [1]

O capítulo retoma a definição já vista na Aula 06 e a aplica à troca de mensagens entre componentes.

Componente de software, revisitado

A parte do sistema responsável por executar um único serviço, como validar um CPF, verificar um endereço a partir do CEP, ou gerar um identificador ao gravar dados numa base. É o conceito mais comum ao modelo SOA.

Comunicação entre componentes

Quem envia inicia a comunicação solicitando um processamento; quem recebe verifica o que precisa fazer e executa; ao final envia outra mensagem de volta, com a resposta. Controlar esse tráfego exige uma estratégia.

07 Componente e comunicação

Ponto a ponto e cliente-servidor [1]

As duas primeiras estratégias são unicast: um nó determina quem recebe a mensagem.

ModeloComo funcionaPonto de atenção
Ponto a pontoO nó de origem copia a mensagem e a envia a um nó, ou conjunto de nós, conectados na redeAtraso nas transmissões, perda de sincronismo, escalabilidade inviável
Cliente-servidorA mensagem vai para um servidor, que centraliza o processamento e distribui aos clientesProcessamento em vários servidores pode gerar redundância
A vantagem do cliente-servidor

Os clientes não precisam ficar sempre conectados, o que reduz o uso da rede.

07 Ponto a ponto e cliente-servidor
6

Broadcast e a convergência para o SOA [1]

Broadcast reduz o custo de verificação de recebimento que o unicast exige em cada nó.

Broadcast

Funciona como rádio ou TV: um nó envia, a mensagem fica disponível a todo nó conectado, e só quem deseja a processa. Exige que a rede suporte o envio e que os interessados estejam conectados no momento.

A convergência para o SOA

Combinar vários modelos soma vantagens e desvantagens. Para reduzir o impacto negativo, surgiu um modelo em que os nós desempenham, ao mesmo tempo, os papéis de cliente e servidor: é esse modelo híbrido que torna o SOA popular.

Serviço, no modelo de Arquitetura Orientada a Serviços [1]

SOA, sigla de Service Oriented Architecture, orienta o desenvolvedor a basear o projeto em componentes que executam serviços específicos.

Definição

No modelo SOA, o termo serviço tem significado parecido com o de componente de software: é um componente independente e autocontido, capaz de terminar o que está fazendo independentemente de o resultado ser positivo ou negativo.

Como identificar os serviços

É praticamente o mesmo processo usado para componentes: o projetista identifica quais serviços o software precisa e como eles se comunicam, seja por metadados, seja por mensagens.

07 Serviço no modelo SOA
10

Os três componentes principais do modelo SOA [1]

O SOA se apoia no modelo de comunicação híbrida do Ciclo 1: um nó pode ser, ao mesmo tempo, Provedor e Consumidor.

Provedor de Serviço

Executa um determinado serviço e mantém a rede informada sobre qual tipo de serviço está oferecendo.

Serviço de Descoberta

Armazena a localização dos serviços disponíveis na rede e conecta o serviço solicitado a quem o solicitou.

Consumidor

É quem solicita a execução de um serviço.

07 Os três componentes do SOA
11

Descrição de serviço e as consequências do modelo [1]

Todo Provedor de Serviços define uma Descrição de Serviço: o que ele faz e o que o Consumidor precisa fornecer para usá-lo.

Interface de serviço

Conjunto de métodos invocáveis mais os tipos de dados usados na invocação. Permite que o Consumidor use o serviço sem saber como o Provedor funciona por dentro: é a base do reuso de software no SOA.

Consequências

Sistema distribuído, ambiente heterogêneo, exigindo interoperabilidade por padrões de protocolo e metadados. Resultado: baixo acoplamento, com componentes localizados e invocados dinamicamente.

Quiz de fixação

A Rota Sul expõe a montagem de remessas como um serviço que outros componentes invocam sem conhecer sua implementação. Qual afirmação descreve o conceito de serviço no modelo SOA?
  • A É um conceito completamente diferente de componente de software, sem relação entre os dois.
  • B Tem significado parecido com o de componente de software: é independente e autocontido, capaz de terminar o que faz independentemente de o resultado ser positivo ou negativo.

Laboratório, passo 1: extrair a interface

Em pedido/service, criar a interface PedidoService com as duas assinaturas já existentes. Nenhuma anotação de framework: ela é o contrato, não a implementação.

public interface PedidoService {

  List<Pedido> listar();
}

Laboratório, passo 2: renomear a implementação e o teste que a instanciava

A classe PedidoService da Aula 06 passa a se chamar PedidoServicePadrao e a implementar a interface, mantendo o construtor e a regra de recusar pedido sem cliente.

@Service
@Profile("padrao")
public class PedidoServicePadrao implements PedidoService {
  private final PedidoRepository pedidoRepository;
  public PedidoServicePadrao(PedidoRepository pedidoRepository) {
    this.pedidoRepository = pedidoRepository;
  }
  // registrar(...) e listar(...): idêntico ao da Aula 06
}

Trocar uma classe concreta por interface quebra quem a instanciava: PedidoServiceTest fazia new PedidoService(...), que deixa de compilar quando PedidoService vira interface.

Laboratório, passo 3: ajustar o controlador

Conferir que PedidoController passa a receber PedidoService, a interface, no construtor. Se ele ainda importar PedidoServicePadrao em algum lugar, a separação não terminou.

@RestController
@RequestMapping("/pedidos")
public class PedidoController {
  private final PedidoService pedidoService;
  public PedidoController(PedidoService pedidoService) {
    this.pedidoService = pedidoService;

  // listar() e registrar(...): idênticos aos da Aula 06
}

O que muda não é o nome: pedidoService já era o nome do parâmetro na Aula 06. O que muda é o tipo que esse nome designa.

Laboratório, passo 5: criar a segunda implementação

PedidoServiceComAnaliseDeRisco, anotada @Service e @Profile("risco"). Mantém a regra herdada e acrescenta a recusa de lojista bloqueado.

@Service
@Profile("risco")
public class PedidoServiceComAnaliseDeRisco implements PedidoService {
  private static final Set<String> LOJISTAS_BLOQUEADOS = Set.of("LOJISTA-BLOQUEADO");
  // construtor idêntico ao de PedidoServicePadrao
  public Pedido registrar(Pedido pedido) {
    // mesma checagem de cliente vazio de PedidoServicePadrao, mais:
    if (LOJISTAS_BLOQUEADOS.contains(pedido.getCliente())) {
      throw new IllegalArgumentException("Pedido de lojista bloqueado por análise de risco é recusado.");
    }
    return pedidoRepository.salvar(pedido);
  }
  // listar(...): idêntico ao de PedidoServicePadrao
}

Laboratório, passo 7: estender a suíte para cada implementação

Duas classes concretas, cada uma implementando criarServico() para devolver a sua própria implementação, com um PedidoRepositoryEmMemoria novo a cada teste.

class PedidoServicePadraoContratoTest extends PedidoServiceContratoTest {
  protected PedidoService criarServico() {
    return new PedidoServicePadrao(new PedidoRepositoryEmMemoria());
  }
}
class PedidoServiceComAnaliseDeRiscoContratoTest extends PedidoServiceContratoTest {
  protected PedidoService criarServico() {
    return new PedidoServiceComAnaliseDeRisco(new PedidoRepositoryEmMemoria());
  }
}

./mvnw test: os dois métodos da classe abstrata executam duas vezes, uma para cada implementação, e as quatro execuções precisam passar.
